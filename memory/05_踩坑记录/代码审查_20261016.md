## 一、P0 功能性缺陷

### P0-1　`PerkUIController.OnChange` 是空挂点，却被计为「成功」

| 项 | 内容 |
|---|---|
| 位置 | `PatchRegistryTable.cs:68` |
| 现状 | `Prefix = null, Postfix = null`（全库唯一一条两者皆空的条目） |
| 证据 | 运行日志 `[Patch自检]   PerkUIController.OnChange` —— **无 `→ Prefix/Postfix` 后缀**，且 `失败 0` |
| 原因 | `ManualPatcher.TryPatch` 对全 null 不做校验，`_harmony.Patch(method, null, null, null)` 被 Harmony 接受、返回 true → `MarkOk()` |
| 影响 | ① 该条目实际什么都没挂；② 自检输出「全部补丁已应用 ✅」是**假阳性**——这正是自检机制本来要防的那类静默失败；③ 与之配对的 `FinalizerPerkUiOnChange` 成了孤儿（见 P0-2） |
| 建议 | ① `PatchEntry` 增加 `Finalizer` 字段，`ApplyAll` 透传 `finalizer:`；② 本条目改为 `Finalizer = "FinalizerPerkUiOnChange"`；③ `TryPatch` 在 `prefix==null && postfix==null && finalizer==null` 时直接 `MarkFail(..., "空挂点")` 并返回 false，杜绝再犯 |

### P0-2　全库 5 个防御性 Finalizer 从未接线（死代码）

| 位置 | 方法 | 目标 |
|---|---|---|
| `Patches.Lifecycle.cs:387` | `FinalizerPerkUiOpen` | `PerkUIController.OpenUI` |
| `Patches.Lifecycle.cs:397` | `FinalizerPerkUiOnChange` | `PerkUIController.OnChange` |
| `BatchDragUpgrade.cs:154` | `FinalizerEndGroupDrag` | `ItemMultiSelectHandler.EndGroupDrag` |
| `LuckScoutPerk.Scavenge.cs:235` | `FinalizerGetRandomScavengedItem` | `ScavHelper.GetRandomScavengedItem` |
| `RobinCrusoePerk.Scavenge.cs:132` | `FinalizerGetRandomScavengedItem` | 同上（另一宿主） |

- **证据（git 考古）**：`git grep -n finalizer c23d33f^ -- "*.cs"` 只命中 `ManualPatcher.cs` 自身三行（形参、`HarmonyMethod`、`Patch` 调用）。
  → **任何历史版本都没有任何调用方传过 `finalizer:`**。这不是阶段6迁移丢失，而是从写下起就没接线。
- **根因**：`PatchEntry`（`PatchRegistryTable.cs:18-31`）没有 `Finalizer` 字段；`ApplyAll`（`:335-336`）只传 `parameterTypes/patchHost/priority`。`ManualPatcher.TryPatch` 虽支持 `finalizer`，却成了无调用方的能力。
- **影响**：这些「保险丝」全部失效。例如 `FinalizerPerkUiOpen` 的原始目的（注释 `Patches.Lifecycle.cs:385-386`）是拦住 `PerkUIController.OpenUI` 内部 `LocHelper.Get()` 异步本地化未就绪导致的崩溃，防止整个特性界面死掉——**目前该保护不存在**。
- **建议**：同 P0-1 加字段并逐条接线；`TryPatch` 已具备能力，改动量很小。

### P0-3　`GameItemElement.ResolveSpriteByName` 槽位错配（Prefix 槽填了 Postfix 方法）

| 项 | 内容 |
|---|---|
| 位置 | `PatchRegistryTable.cs:235` → `Prefix = "PostfixResolveSpriteByName"` |
| 方法定义 | `WageGirlSystem.Anim.cs:484`：`static void PostfixResolveSpriteByName(GameItemElement __instance, string name, ref Sprite __result)` |
| 原因 | 该方法用 `ref Sprite __result` 写返回值 —— 这是 **Postfix 语义**。作为 **Prefix**（返回 void、不跳过原方法）时，`__result` 是原方法的**默认返回值**，原方法执行后用自己的返回值把它**覆盖**掉 |
| 影响 | 「对蛙娘永远返回 mod 图标」的覆盖**从未生效**。立绘视觉上未必可见（另有 `PrefixApplyAnimationFrame`，`PatchRegistryTable.cs:234` 走 `ref Sprite frame` 的另一条路径兜住），但这条挂点纯属空转 |
| 建议 | 改为 `Prefix = null, Postfix = "PostfixResolveSpriteByName"` |

## 二、P1 结构性风险

### P1-1　同方法多 Prefix 且同优先级（400）→ 执行顺序未定义

扫描结果（同 `Target.Method` 上有 ≥2 个 Prefix，且 priority 全为 `DEFAULT_PRIORITY`）：

| 目标 | Prefix 数 | 宿主 |
|---|---|---|
| `GameItem.Target` | **7** | DestinyDice, TurboBoostN×2, WageGirlSystem, RobinCrusoePerk, ContainerUpgradeV2, LuckScoutBackpackUpgrade |
| `RenderHandler.LoadFromAtlas` | **6** | Patches, LuckScout, DestinyDice, GuMachine, WageGirl, WageBrother |
| `GameItem.CanTarget` | 5 | — |
| `GameItem.MayTarget` | 5 | — |
| `GameItem.MayHaveValidInventorySlot` | 4 | — |
| `PlayerStore.AddDirectSellingItemToTable` | 2 | WaterMerchant, ThiefMagnet |

- **`RenderHandler.LoadFromAtlas` 是本类里最危险的一条**：6 个宿主都是
  `bool PrefixLoadFromAtlas(string atlasPath, string name, ref Sprite __result)`，
  命中自己认领的 sprite 名时 **`return false`**（例：`WageGirlSystem.Anim.cs:189`、`Patches.Lifecycle.cs:612`）。
  Harmony 的 Prefix 在**首个返回 false 时短路，后续 Prefix 全部跳过**。当前 6 者过滤的名字互不重叠（`custom_storage_box_sprite` / `ICON` / 各自名字），**暂未触发**；但一旦两个宿主认领同一个 sprite 名，靠后者会被**静默跳过**，且顺序不由声明顺序保证。
- **对照证据**：`HealthData.ReceiveMinorWound` / `ReceiveMajorWound` 已经显式用了 priority `100`（`WageBrokerPermitPatches`）vs `400`（`RobinCrusoePerk`），并在 Note 里写明「顺序依赖→显式约定」（`:109-111`、`:164-167`）。说明团队知道要显式排序，只是**没有推广到上表**。
- **建议**：凡存在「短路语义」或「相互依赖」的多挂点，显式设 priority 并写进 Note；或收敛为单一「路由器」Prefix，由它按名字分派，从根上消除顺序依赖。

## 三、P2 清洁度 / 文档漂移

### P2-1　`Core.cs:80-87` 假成功日志

```csharp
try { Log.Msg("[Patch] 蛙哥牛逼特性补丁应用成功（AddClient/DismissClient/NewDay）"); }
catch (System.Exception ex2) { Log.Msg("[Patch] 蛙哥牛逼特性补丁应用失败: " + ex2.Message); }
```
try 块里**只有一句 `Log.Msg`**，永不抛异常 → 无条件打印「应用成功」。这是早期内联挂载的残留（挂载早已迁入注册表），属于**误导性日志**：看日志的人会以为这里有 3 个挂点生效。**建议删除整段。**

### P2-3　`UseByName` 会静默丢弃 `Priority`

- 位置：`ManualPatcher.cs:117-147`（`TryPatchByName` 只接 `prefix/postfix/patchHost`）；调用点 `PatchRegistryTable.cs:331`
- 现状：6 条 `UseByName=true`（`PatchRegistryTable.cs:255/257/258/260/261/262`）**全部是 `DEFAULT_PRIORITY`**，故**当前无实际损失**
- 风险：隐性陷阱 —— 谁给这类条目设自定义 `Priority` 都会被无声忽略；同理 `ParameterTypes`、`finalizer` 也不支持（当前无条目同时使用，已扫描确认）
- 建议：给 `TryPatchByName` 补 `priority`/`finalizer` 形参并在 `ApplyAll` 透传；或加断言：`UseByName && Priority != DEFAULT_PRIORITY` 时报错
