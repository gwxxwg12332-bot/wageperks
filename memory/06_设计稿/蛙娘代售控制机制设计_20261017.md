## 0. 一句话方案

给玩家一套「售货规矩」＝ **单件标记（实例级）+ 规则名单（存档级）+ 全局模式（开关级）** 三层控制；
冲突时按 **「硬锁不可覆盖 → 具体性优先 → 同级禁止优先」** 三条原则裁决。

> ⚠️ **v2 关键修正**：**判定权威层是「规则名单」，不是「单件 tag」**。
> tag 因随档性未实锤（§2 层 A），只承担 **UI 快捷层**；名单承担真正的保护判定。
> 两条路线由拆包结论二选一，引擎侧用同一开关切换，不动架构。

## 2. 数据模型：三层规则

### 层 A —— 单件标记（实例级 Tag）⚠️ **定位已降级：仅作快捷层，不作唯一保护手段**

> **2026-10-17 审阅修正**：原稿据 `ContainerUpgradeV2.Detect.cs:42` 断言"tag 随档持久化"，**依据不充分**。
> **同文件存在反例**：
> - `:29`「老档蛙哥箱（旧版创建）可能缺 `CUSTOM_STORAGE_TAG`（**ES3 不保证 tag 保留**），用 identifier 兜底」
> - `:33`「10-13 Step4④：读档后**场景物品 tag/identifier 全丢**（拆包实锤）→ `WBG_BOX_TAG` 独立随档身份兜底」
>
> 即 **tag 随档性「因 tag 而异」，且可能「因店内物品 vs 场景物品」而异**。
> `WAGE_NO_SELL` / `WAGE_FORCE_SELL` 是**全新自定义 tag，随档性未实锤** → 终审已并入 `AUDIT-P1-2-E §二-5`。

| Tag 常量 | 语义 | 定位 |
|---|---|---|
| `WAGE_NO_SELL` | 免售（保护这一件） | **快捷层**（UI 反馈 + 快速开关） |
| `WAGE_FORCE_SELL` | 必售（优先卖这一件） | **快捷层** |

**两条实现路线（按拆包结论二选一，引擎侧用 `UseTagAsMarker` 开关切换）**：

- **路线甲（拆包结论 = tag 随档）**：tag 直接作为单件标记，随档持久，零额外存储。
- **路线乙（拆包结论 = tag 不随档 / 不确定）**：**层 B 名单为唯一判定来源**，tag 降级为**纯 UI 层**
  （只负责"玩家点一下就有视觉反馈"，不承担保护职责）。
  - 具体做法：玩家"打标"时，同时把该物品 `identifier` **写入层 B 名单**（`Protect.id:<identifier>`），
    由名单完成真正判定；tag 只用于 tooltip 角标与面板勾选态显示。
  - **代价（必须接受）**：名单按 `identifier` 匹配 → 同 id 的多件物品**会一起被保护**（无法只保护其中一件）。
    对"可堆叠/多件同类"物品这是可接受的降级；若需精确到单件，只能等路线甲。
  - **叠加恢复钩子**（§5）：读档后按名单对柜台物品**补打 tag**，使表现层与判定层重新一致。

- **共同代价**：tag 绑定实例，物品被**拆分/复制**时不自动继承 → 需恢复钩子（见 §5）
- **注意**：与现有 `wage_bro_card` / `destiny_dice_tag` / `MODULE_STUCK_TAG` 等 tag 不冲突（不同命名空间）

### 层 B —— 规则名单（存档级，`WageSaveStore`）★ **判定权威层**

命名空间 `WageGirlSell`，**一条规则一个 key**（便于 `EnumerateKeys` / `RemoveKey` 精确增删，
避免逗号串的转义与"全量重写"问题）：

| key | 类型 | 默认 | 说明 |
|---|---|---|---|
| `Protect.<n>` | string | 空 | 免售规则串（n 自增） |
| `Allow.<n>` | string | 空 | 可售规则串 |
| `Mode` | int | 0 | 0 = 黑名单模式（默认，=现状）；1 = 白名单模式（仅售 Allow） |
| `PickOrder` | int | 0 | 0=列表序(现状) / 1=最便宜 / 2=最贵 / 3=随机 |
| `DailyQuota` | int | 1 | 每日代售件数（现状硬编码 1） |
| `AutoSellOn` | bool | true | 代售总开关 |

> 备选（对齐房规 `BuildConfig.cs:142` `WageBrotherCustomBuyIds` 的逗号串风格）：单 key 存整串。
> **推荐一 key 一规则** —— 增删单条不必重写整串，且天然支持 `EnumerateKeys` 展示。（总控已批准）

**规则串语法**（一条规则覆盖一类，避免逐 id 堆积）：

| 形式 | 匹配 | 示例 |
|---|---|---|
| `id:<identifier>` | 精确物品 | `id:void_bead_storage` |
| `tag:<TAG>` | 带该 tag 的全部物品 | `tag:MODULE_TAG`（所有模组，一条搞定） |
| `cat:<类别>` | 语义类别 | `cat:contraband` / `cat:food` / `cat:drink` / `cat:weapon` |
| `val:<min>-<max>` | 价值区间 | `val:0-50`（只动低价废品） |
| `*` | 全部 | 白名单模式下 `Allow.*` = 全部可售 |

- **匹配键** = `GameItem.identifier`（稳定 id，如 `void_bead_storage`）；显示名走 `name` / `ModCannibalism.GetName`
- `cat:` 复用现有判定：`ItemHelper.IsFood/IsDrink`、`ContrabandHelper.GetContrabandLevel`

#### 🚫 键设计硬约束（总控 2026-10-17 签发，不可违反）

**名单键一律为「内容规则键」，严禁任何 `loc+idx` 类位置键。**

| | 内容 |
|---|---|
| **允许** | `WageGirlSell.Protect.<n>` / `WageGirlSell.Allow.<n>` —— `n` 仅作**条目序号**，与物品所在库存位置**完全无关** |
| **严禁** | 任何形如 `..._{loc}_{idx}`、`..._{slot}`、`..._at_<库存>_<索引>` 的键，即把状态绑到"物品当前在哪一格" |
| **反例（P0 事故，勿重蹈）** | `ContainerUpgradeV2.Restore.cs:101` 的 `wage_stage_{loc}_{idx}`、`BlackGoldBox.Style.cs:213` 的 `style_{loc}_{idx}` —— 绑库存位置 + 只写不清 + 恢复无身份校验 → **普通容器被误改网格**（详见 `派活单_开发AI_P0_容器误伤根治_20261015.md`） |
| **理由** | 物品在库存间移动/换位后位置键必然错配，且无身份可校验 → 误伤无法收敛 |
| **自检** | 实现完成后 grep 新键名，确认无 `loc` / `idx` / `slot` 参与键构造 |

### 层 C —— 全局模式

- `AutoSellOn = false` → 代售彻底关闭（一键静音，不动其他机制）
- `Mode = 1` 白名单 → **只**卖命中 `Allow` 的；清单为空 = 一件不卖（**UI 必须警告，不得静默**）
- `Mode = 0` 黑名单（默认）→ 除命中 `Protect` 外都可卖

## 3. 冲突裁决（优先级）

**评估顺序，首个命中即定论**：

```
① 硬锁层（玩家不可覆盖）
   AutoSellOn == false                          → 禁售
   违禁品 / ORDER_TICKET_TAG / wage_bro_card /
   destiny_dice_tag / unitValue <= 0            → 禁售   ← 沿用现状硬编码，保证行为不回退

② 单件标记层（最具体）
   IsTag("WAGE_NO_SELL")                        → 禁售
   IsTag("WAGE_FORCE_SELL")                     → 可售

③ 名单层
   命中 Protect                                 → 禁售
   命中 Allow                                   → 可售

④ 模式层（兜底）
   Mode == 白名单 且未命中 Allow                 → 禁售
   Mode == 黑名单 且未命中 Protect               → 可售

⑤ 默认                                        → 可售（等价现状）
```

**三条原则**（写进代码注释，作为后续扩展的判据）：

1. **硬锁不可覆盖** —— 系统级禁止项永远最高优先级。玩家的任何标记/名单都**不能**让违禁品被代售
   （牵涉原版治安部巡查/没收机制，越权会炸经济与剧情链）。
2. **具体性优先** —— 单件 > 名单 > 全局。理由：单件标记是"针对这一件"的即时意图，名单是"一类东西"的
   批量约定；后者修改时不应悄悄推翻前者。
3. **同级禁止优先** —— 同一具体度下冲突（例如同一 id 同时进了 `Protect` 与 `Allow`）→ **禁售胜**。
   理由：**误卖不可逆**（东西没了、钱可能远低于价值），**误不卖只是少赚一次**；不可逆操作一律取保守侧。

> ✅ **已拍板（总控 2026-10-17）**：
> - **② 先于 ③** —— **单件 > 名单**，与"具体性优先"自洽
> - **同级 Protect 胜 Allow** —— 误卖不可逆，同意设计稿
>
> ⚠️ **与 §2 路线乙的耦合**：若拆包结论为"tag 不随档"而走路线乙，则"单件标记"实际由**名单**承载
> （打标即写 `Protect.id:<identifier>`），此时 ② 与 ③ 同源，顺序不再产生分歧（行为等价）。

## 6. 玩家使用流程（回答"如何方便管理"）

| 场景 | 操作路径 |
|---|---|
| 保住收藏品 | 柜台里 **Ctrl+右键**该物品 → 打 `🔒`（tooltip 立刻变） |
| 只清废品 | 面板设 `PickOrder=最便宜` + 规则 `val:0-50` 进 Allow，开白名单模式 |
| 全部模组别卖 | 加一条 `tag:MODULE_TAG` 进 Protect（**一条规则覆盖所有模组**，不用逐个加） |
| 今天别卖了 | 面板关 `AutoSellOn` |
| 每天多卖几件 | `DailyQuota=3` |

**"方便管理"的三个设计要点**：

1. **规则而非枚举** —— 支持 `tag:` / `cat:` / `val:`，避免玩家维护几十条 id
2. **即时可见** —— 打标后 tooltip 立刻变；日报每天报告"卖了什么"或"为什么没卖"
3. **一键批量** —— 面板「把柜台现有物品全加入免售」，把"逐个点"变成一次操作

| 路线乙的代价：同 id 多件会一起被保护 | 接受降级；需精确到单件只能等路线甲 |
| tag 不随拆分/复制 | 需恢复钩子（§5）；或对"可堆叠物品"改走名单而非 tag |
| **位置键误伤（P0 事故教训）** | 键设计硬约束（§2 层 B）：只用内容规则键，禁 `loc+idx`；实现后 grep 自检 |
| 白名单空清单 → 一件不卖 | UI 必须警告（否则玩家以为坏） |
| 规则存 runID 分区 → 新档不继承 | 默认合理；可选"全局命名空间" |
| 性能 | 柜台 `childItems` 通常 <50；但 `EnumerateKeys` 逐件调用会 O(n·m) → **打烊结算时一次性读进内存 `HashSet`**，循环内纯内存匹配 |
| 不碰的机制 | `YieldMod` 让路（WS/WP 双装）、`WageGirlAutoMove`、`K_SALE_DAY` 语义 —— 本机制只改"**选谁卖**"，不改"**什么时候卖**" |
| 兼容性 | 默认值 = 现状（黑名单模式 + 空名单 + `first` + `Quota=1` + 总开关开）→ **零配置玩家体验完全不变** |
